## Agent architecture
- NOT a screen-driven ReAct loop. Plan-then-execute: LLM writes a JSON Plan (steps w/ `action` from a typed catalogue ActionSchema.kt (1,572 lines), params, dependsOn, fallback) -> PlanValidator (registered? auto-fix some names; contact resolution inserts ASK_USER step) -> proposal/approval (AutoMode OFF/AUTO(allowlist all-or-nothing)/YOLO(bypasses everything incl. neverAutoApprove)) -> executePlanLoop (ActionDispatcher executes steps; per-step LLM "re-evaluation" CONTINUE/MODIFY/ABANDON; MODIFY merges new steps and, if autoApproved, RE-CHECKS pending steps against the allowlist so injected steps cannot bypass it) -> memory/log with privacy redaction (ExecutionHistoryPrivacy, CrashLogRedactor).
- Risk lattice ActionRisk {UNSPECIFIED, READ_ONLY, REVERSIBLE, SENSITIVE, ADVANCED_CONTROL, IRREVERSIBLE}; `allowsAutomaticFallback(risk)` only for READ_ONLY/REVERSIBLE: "A provider switch can change plan semantics" — high-impact plans never cross a provider boundary automatically; fallback providers = explicit user allowlist ("The app does not infer permission to send a prompt to another vendor from the presence of an API key").
- Other: IntentClassifier + "Compound Intent Guard", ContactResolver (4-tier fuzzy), AliasResolver, AutoReplyEngine (reads notifications, replies via LLM with `<untrusted_message>` tags + sanitize + non-overridable security rules), HabitRoutineEngine (records app-open sequence from a11y events; 30-min clustering; proposes routines), 4-tier "knowledge graph" memory (Level 4 = Keystore-encrypted), voice (wake word/STT/TTS), 7-network social manager (partly simulated).
- App-specific "automators" (WhatsApp/Telegram/SMS) hard-code view ids (`com.whatsapp:id/entry`, `/send` ...) + fixed `delay(3000)`; post-send check "input field now empty" (nice idea, brittle impl).
- A11y service mechanics: findAccessibilityNodeInfosByText/ViewId then ACTION_CLICK on node or first clickable ancestor (unbounded parent walk); ACTION_SET_TEXT unverified; `dispatchGesture(gesture,null,null)` fire-and-forget (100 ms tap); scroll = first scrollable node in tree order, ACTION_SCROLL_FORWARD/BACKWARD; `performImeEnter()` = ACTION_IME_ENTER (API 30+) else click a node labelled search/go/send/done/submit/ok/enter; node.recycle() everywhere; screen-off/keyguard receiver hides overlay. NOT a better action engine than AutoHost's/ClosePaw's.
- UI trick worth noting (their issue #107): floating overlay = TWO TYPE_ACCESSIBILITY_OVERLAY windows: a FLAG_NOT_TOUCHABLE draw layer + a smaller touchable window matching the icon's footprint, so transparent margins never swallow taps meant for the app underneath. (AutoHost BubbleOverlay should be checked for this dead-zone.)
- LLM providers: 13 (Gemini, Claude, OpenAI, Groq, DeepSeek, Mistral, OpenRouter, Together, Cohere, GitHub Copilot, "Opencode-Go", Ollama, custom OpenAI-compatible) via Retrofit/OkHttp; ProviderCatalog, ProviderSelectionPolicy, ModelFetcher (dynamic model lists), LLMError taxonomy. Keys: direct Android Keystore AES-256-GCM envelopes (`KeystoreSecretStorage.kt` 384 lines; random 96-bit IV, AAD = credential id, versioned envelope, "zero plaintext fallback", setUserAuthenticationRequired(false) because background requests; separate alias+file per store; retired EncryptedSharedPreferences). Reported "CredentialsMustBeReentered" state on envelope/key failure.
- In-app MCP server (McpServer.kt, 330 lines): raw ServerSocket on 127.0.0.1:8765, header `X-OpenDroid-Token` compared via SHA-256 digests + MessageDigest.isEqual, 1 MiB body cap, 15 s timeout, single-thread accept loop, JSON-RPC protocol 2024-11-05. Tools include `execute_action`, **`run_privileged_command` (Shizuku/root/app shell)**, `terminal_create/write/read`, `mcp_configure` (persist outbound MCP endpoints w/ headers). => any local app that obtains the token gets a shell. Loopback is reachable by every app on the device. DO NOT copy this exposure; AutoHost's Dev API/MCP must keep its own token+scope+no-shell-by-default posture (check core/devapi threat model).
- Manifest: ~45 permissions (CALL_PHONE, SEND_SMS, READ_SMS, QUERY_ALL_PACKAGES, ACCESS_BACKGROUND_LOCATION, WRITE_SETTINGS, SYSTEM_ALERT_WINDOW, PACKAGE_USAGE_STATS…), allowBackup=true with extraction rules excluding prefs/db/datastore, largeHeap=true. NSC: cleartext ONLY localhost/127.0.0.1/10.0.2.2 (doc and file agree — good; but LAN servers (192.168.x) are therefore HTTPS-only).

## On-device inference (the part most relevant to AutoHost phase 13)
- Engine: `com.google.ai.edge.litertlm:litertlm-android:0.14.0` — classes Engine, EngineConfig(modelPath, backend, maxNumTokens, cacheDir), Backend.GPU()/CPU(), Conversation/ConversationConfig/SamplerConfig(topK 40, topP .95, temp, seed 0), sendMessage / sendMessageAsync(Flow). Artifact ships ABIs x86_64 + arm64-v8a ONLY (per their QA doc E3). Model files `.litertlm` / `.task`.
- Catalogue (pinned revisions + exact sizes + SHA-256, all "recorded from HF endpoints, not yet re-hashed from downloaded bytes" except Qwen): Gemma 4 E2B-it (2,588,147,712 B; minSdk 31; ctx 4096; ungated litert-community mirror), Gemma 4 E4B-it (3,659,530,240 B; minSdk 31; ctx 4096), Gemma 3n E2B (3,655,827,456 B; gated; ctx 4096), Gemma 3n E4B (4,919,541,760 B; gated), Qwen2.5-0.5B-Instruct q8 ekv1280 `.task` (546,660,344 B; minSdk 26; ctx **1280**). RAM gate by file size: >=3 GB file needs 8 GB total RAM, >=2 GB needs 6 GB, >=1 GB needs 4 GB (their heuristic on TOTAL RAM, not available).
- => **Context windows 1,280–4,096 tokens are far too small to carry an accessibility-tree agent loop** (system prompt + tool schemas + one screen dump already ~1–3K tokens) and the usable models need >=6 GB RAM + API 31. A 0.5B model at 1.3K ctx cannot plan UI tasks. Honest conclusion for AutoHost devices (Realme C3 API 30 / Galaxy M31 API 31): local LLM = small helper (extraction/classification/short planning of capability calls), NOT an agent loop, until a device spike proves otherwise.
- Provider design flaws: one new Conversation per request (no KV-cache reuse across agent steps => full prefill each step); tool calling by prompt-engineered JSON only if whole reply starts with `{` and ends with `}`; `@Synchronized` blocking inference; engine cached with model path; tries GPU then CPU (no per-model backend metadata); `LiteRtCompatibility.verify` loads the whole engine to "verify" a file and classifies failures by English substrings of exception messages (v1.0.6 changed `.all` -> `.any` match "to fix false FORMAT_INVALID" = weakened check).
- Integrity pipeline (GOOD, adaptable): `ManagedModelArtifactMetadata.isComplete` requires pinned 40-hex revision in the `resolve/<rev>/` URL path, https, no userinfo, size>0, 64-hex sha256; partial metadata => managed download unavailable. Install manifest JSON (schema_version, model_id, filename, install_source MANAGED_DOWNLOAD|LOCAL_IMPORT, byte_size, sha256, download_url, source_revision), atomic same-dir replace w/ fsync, `verifyForStartup` (size) and `verifyBeforeNativeLoad` (SHA-256 before the native engine sees the file), `CachingFileHashVerifier`; local imports keep only a fingerprint and "do not claim publisher provenance". ModelDownloadWorker: WorkManager foreground (dataSync FGS), Range-resume with Content-Range check, size cap (abort if payload exceeds published size), fsync, stop => retain partial, verify hash+size, then install + format probe; HF token (Keystore) attached as Bearer; temp file in cacheDir (weak: cache can be evicted; use noBackupFilesDir). Latency profile: p95 of last <=20 samples per device+model tier (min 3 samples) => "budget exceeded" notice.
- Their QA plan structure (E1–E6 environment gate, A1–A9 acquisition, B1–B10 inference, C1–C6 failure, D1–D5 switching) is a good template for AutoHost's S6 local-inference spike (clean-room reuse of the TEST IDEAS; Apache doc can also be adapted with attribution).
