## How to use this tracker
1. Work phases **in order**. Do not tick a task in phase N+1 until all **gate** items of phase N are ticked with evidence (`--check` fails otherwise).
2. A task is ticked only when code, tests, docs and evidence are done (see `AGENTS.md` §5).
3. Sizes: `[S]` = 1 point, `[M]` = 2, `[L]` = 4. Gates count 2 points each. Progress % is weighted by these points.
4. **Evidence:** every `[M]`/`[L]` task and every gate item has an `  - evidence:` line — fill it (commit hash, test name, log/screenshot path, device + API level). A ticked item with an empty evidence line fails `--check`.
5. In-progress: add `(WIP)` after the ID. Blocked: add `(BLOCKED: reason)` and list it under **Blockers**.
6. IDs are stable; never renumber. Add new tasks at the end of a phase with the next number.
7. After ticking: `python tools/progress.py` then `python tools/progress.py --check`; optionally `--html docs/progress.html` for a visual dashboard.
8. At the start of an authorized phase, record its dated **IN PROGRESS** start in `../TRACKER.md`. Do not start a phase or app-code implementation without explicit user authorization.
9. At the start of every batch, mark it **IN PROGRESS** in `../TRACKER.md`. After each meaningful change and each individual check, record the exact command and observed result there before proceeding.
10. Keep this phase/task checklist and `../TRACKER.md` consistent. Preserve failed checks, blockers, decisions, and deferred work; never erase history.
11. Before finishing a batch, compare the checkboxes and evidence here with the actual code and test results. Leave incomplete or unverified items unchecked and explain why.

In this workspace, the source pack is under `plan/`. From the workspace root, run tracker commands as `(cd plan && python tools/progress.py --check)`; use `(cd plan && python tools/progress.py)` to regenerate the dashboard.
