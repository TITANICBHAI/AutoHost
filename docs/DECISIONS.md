### ADR-021 — App licence: Apache-2.0 (accepted)
- **Context:** D-02 / AGENTS §7 require a licence decision. The owner asked for the best choice.
- **Decision:** AutoHost's own code is licensed Apache-2.0.
- **Why:** every third-party component we plan to reuse is Apache-2.0 or MIT (Chaquopy, Maestro/Appium ideas, Mobilerun ideas). Apache-2.0 is permissive, compatible with both, includes an explicit patent grant, and does not pull in AGPL/GPL terms. The clean-room rule for Mobilerun Portal (AGPL) and OpenAutoJs (GPL + NC) still applies.
- **Consequences:** add the Apache-2.0 `LICENSE` file at the repo root in task P1-01; keep `THIRD_PARTY_NOTICES.md` current; the licence CI check (X-02) must reject AGPL/GPL dependencies. Revisit only if a required dependency forces a different licence.

### ADR-032 — Selector P3 semantics: BFS ordering, `index` relation, bounds modes
- **Context:** P3-01 required the full match-mode set (plan §7.6). `Selector.algorithm` existed in the wire schema but the engine ignored it; the plan lists `bounds (inside/overlaps)`, `drawing_order`, and `index` among numeric/relational filters, but `index` has no anchor semantics elsewhere in the plan.
- **Decision:** `algorithm: "bfs"` orders *surviving* matches shallowest-first (then document order); the deepest-match ambiguity rule still collapses ancestor chains before ordering. `relation {kind:"index", n}` means "this node is the n-th (0-based) match of the anchor selector in document order" — the node itself is a candidate (spatial relations exclude self; index includes it). `BoundsFilter.mode` is `inside` (default) or `overlaps` with open sides unbounded. Schema (`broker.schema.json`), Kotlin engine and the sim mirror (`autohost_sim/match.py`) all encode these rules; the sim keeps "no deepest-match/BFS" as a documented simplification.
- **Consequences:** `sel.index_at(anchor, n)` in the SDK is a positional pick across the anchor's matches; scripts that relied on `bounds` being a no-op in the sim (it now filters) must supply real coordinates — samples already do.

### ADR-033 — ReadGate: single-flight + sacrificed workers, policy pure
- **Context:** plan §5.7 requires bounded reads with degraded snapshots; a wedged framework read cannot be cancelled.
- **Decision:** `ReadGatePolicy` is pure (maxConcurrent=2, budget 2.5 s) and exhaustively tested; `ReadGate` runs reads on a bounded pool keyed by scope, joins concurrent readers (single-flight per key), abandons the *waiter* at the budget while the read keeps running on its own dispatcher (worker sacrificed, slot reclaimed on completion), and serves the last good snapshot with `meta.degraded/degraded_reason/snapshot_age_ms`. A degraded result with no history raises `TIMEOUT` honestly.
- **Consequences:** a wedged read keeps a pool slot until the framework call returns; saturation degrades other scopes rather than queueing unboundedly.

### ADR-034 — IME as its own `:capabilities:ime` module with a bridge, no AIDL
- **Context:** the AutoHost keyboard must commit text from the background and own clipboard reads on API 29+ (only focused app + default IME may read). Chaquopy restricts library modules, so the IME needed a home.
- **Decision:** `:capabilities:ime` hosts `AutoHostKeyboardService` (1 px input view, never fullscreen), `InputConnectionTextEditor` (commit + verify logic, testable), `ImeBridge` (process-local request queue, same shape as `A11yBridge`) and `ImeProvider` (`device.ime`). Outcomes come from `textInputOutcomes`; unverified commits are reported (`TEXT_INPUT_UNVERIFIED`), never assumed. The a11y `set_text` chain consumes the bridge through a small `TextEntryBackend`/`ClipboardAccess` interface defined in `:capabilities:a11y` — no cross-capability dependency.
- **Consequences:** selection state is read from secure settings (`ImeSelector`); enabling the IME stays a user action until the P4 secure-settings self-heal. Verification of the field read-back is bounded (4 KB window) to avoid stalling on huge fields.

### ADR-035 — Screenshot chain lives in `:capabilities:projection` with an injected a11y hook
- **Context:** the chain is a11y (API 30+) → MediaProjection → T3 later; `:capabilities:projection` must not depend on `:capabilities:a11y` (dependency direction, CONVENTIONS.md).
- **Decision:** `ProjectionScreenshotProvider` (`device.screenshot`) takes `a11yActive`/`a11yCapture` lambdas; `AppGraph` wires them to `ScreenshotA11yApi30`. `ProjectionHolder` owns the MediaProjection session (started by `ProjectionService`, FGS `mediaProjection`, consent via `ProjectionConsentActivity`); `Screenshotter` does the pure bitmap work (crop/scale/PNG). Throttling (`ScreenshotThrottlePolicy`: 1 s interval, burst 3/min) runs before any capture; secure screens raise `SCREENSHOT_BLOCKED` with `SECURE_SCREEN`. The consent activity uses the platform translucent theme instead of `Theme.AutoHost.Transparent` (the designsystem theme is not visible to capability modules — doc deviation noted in ANDROID_MANIFEST.md).
- **Consequences:** `ProjectionHolder` uses `System.currentTimeMillis` for the granted-at stamp (framework object lifetime only, no ordering logic depends on it); AutoAcceptGate clicks the consent dialog only while a flow is pending (ADR-036).

### ADR-036 — AutoAcceptGate: policy-pure, pending-flow-gated, spike-verified ids
- **Context:** plan §5.7 — the gate clicks known system dialogs *only while a host-initiated flow is pending*, with cooldown + rate limits. Dialog view ids differ across OEMs/API levels.
- **Decision:** `AutoAcceptPolicy` (pure) owns every safety rule: no pending flow ⇒ no click; only `PopupGuardPolicy.KnownDialog` matches; 60 s failure cooldown; ≤4 accepts/min; give up after 3 attempts per flow. `MediaProjectionAutoAccept` matches by view id with localized label fallback; the id list is explicitly spike-verified at Gate 3-e (S3 notes in SPIKES.md) — until then the gate may stand down more often than it should, which is the safe direction.
- **Consequences:** dismiss_unknown_dialogs is deliberately not implemented (never click unrecognized windows); `dismiss_known_dialogs` in task config maps to `PopupGuardPolicy.Mode.DISMISS_KNOWN` and only works when the dialog's package is inside the granted scope (fail closed).

### ADR-037 — Stop chain honesty: VERIFIED only on observed foreground exit
- **Context:** P3-20; `stopResults` = VERIFIED/BEST_EFFORT/FAILED. Android gives no reliable cross-app process-liveness API to a normal app.
- **Decision:** the chain is `kill_background` (best-effort, unverifiable) → App-info UI path (drives Force stop + confirm over a11y, wired in AppGraph so `:capabilities:app` stays independent). `VERIFIED` means the tracked foreground left the target package; otherwise BEST_EFFORT; exhausted strategies = FAILED (`STOP_FAILED`). `strategy:"shell"` is refused with `SHELL_TIER_NOT_PAIRED` until Phase 9.
- **Consequences:** a background app killed silently reports BEST_EFFORT even though it worked — honest over optimistic; the UI path is device-verified at G9-a.

### ADR-039 — Schedule engine: Python reference + shared golden vectors, cron restricted-field semantics
- **Context:** P4-01/P4-16 need schedule math the JVM tests can trust, and HANDOFF §4 required the `autohost_ref` implementations to be written first (the P3 pattern: Python reference + Kotlin engine + shared vectors).
- **Decision:** `sdk-python/autohost_ref/schedule.py` is the normative reference; `tools/gen_schedule_vectors.py` generates `testing/golden/schedule_vectors.json` (43 cases: every rule type, limits, misfire, fan-out, conditions), and `ScheduleEngineGoldenTest` (:core:engine) asserts the Kotlin engine matches case by case — same contract as the compact-dump golden test. Two semantics the vectors pin: (a) **cron dom/dow OR applies only when BOTH fields are restricted** (standard Vixie behaviour — `30 4 * * 7` fires only on Sundays; a `*` field never blocks); dow 0–7 with 0 and 7 = Sunday. (b) **max_runs_per_day blocks only the counter day** (`state.day_key`): interval rules count UTC days, zoned rules count rule-tz days; previews assume future days start at zero runs.
- **Consequences:** regenerating the vectors requires a recorded decision (they are a cross-implementation contract, not a snapshot); interval `window`-type rules anchor their grid at window start, not at the rule anchor; `end_at`/`max_total_runs`/`stop_after_consecutive_failures` exhaust a rule to `null` (the controller then disarms and records `FINISHED`).

### ADR-040 — DB v2: trigger rules + schedule state/events as separate tables

### ADR-041 — Scheduler backends: interface in `:core:engine`, Android classes injected from `:app`
- **Context:** P4-05 needs pluggable backends (plan §11.3) but `:core:engine`'s JVM tests must stay Robolectric-free, and WorkManager/JobScheduler fire targets need app-level classes.
- **Decision:** `SchedulerBackend` (interface), `ExactAlarmPolicy` (pure choose/near-window rules) and the misfire/reconcile policies live in `:core:engine/schedule/`; `AlarmBackend`/`WorkBackend`/`JobBackend` are Android classes in the same package that take their worker `Class`/`ComponentName` from `:app` at construction. ### ADR-042 — ScreenGuard: policy-pure, service in `:capabilities:screen`, recovery activity for dismissal
- **Context:** P4-10 (§11.6): wake a sleeping/unlocked screen for scheduled UI runs without ever fighting a secure lock. `requestDismissKeyguard` requires an Activity, so a bare service cannot dismiss keyguards.
- **Decision:** `ScreenGuardPolicy` is a pure decision table over `(enabled, interactive, deviceLocked, secureLock, lastAttemptAt, now, lastVerdict)` → `NOOP | WAKE_ONLY | RECOVER | DEGRADED(SECURE_LOCK)` (60 s throttle; RECOVER only after a recent WAKE_ONLY failed to clear the lock). `ScreenGuardService` (FGS specialUse) holds a steady `SCREEN_BRIGHT_WAKE_LOCK|ACQUIRE_CAUSES_WAKEUP`, re-evaluates every 30 s + on screen/user broadcasts, and starts `ScreenGuardRecoveryActivity` (`showWhenLocked`+`turnScreenOn` in the manifest) guarded by a generation token and a 5 s timeout for non-secure dismissal. Secure locks degrade loudly (`WAITING_USER(unlock)` notification) — never silent retry. The service clock is injected (`ScreenGuardService.clock`, A11yBridge pattern).
- **Consequences:** G4-g is provable at the policy level on the JVM; the wake-lock-while-enabled behaviour is the always-on recipe's fallback (the recipe checklist, P4-13, remains the supported path); the guard service is started from Settings, not implicitly.

### ADR-043 — Scheduled-fire gating: preflight + UI lock live in the `:app` start path; manual runs bypass
- **Context:** P4-08/P4-09: locks (§11.4) and preflight (§11.5) must gate scheduled fires, but `RunOrchestrator` is runtime-agnostic and manual runs are user-initiated (the user can already see the device).
- **Decision:** `AppGraph.startRun(taskId, profileId, triggerType)` applies `Preflight` (conditions from the schedule row, screen/unlock policy, UI-lock busy check) and acquires the global UI lock **only when `triggerType == "schedule"`** and the manifest is UI-acting (`ui_exclusive` or `device.ui.act` need). Lock handles are held per run id and released on the run's terminal transition (the same `runStore.runs` stream that owns the run foreground service). Outcomes map per §11.5: Wait → log + skip this fire (bounded retry on the next fire), NeedsUser → `WAITING_USER(unlock)` notification, Skip → `SKIPPED:<reason>` recorded in schedule events. `ctx.next_run` proposals (P4-11) clamp to `execution.min_interval_minutes` (already in task.schema.json) and the rule's conditions window, store as `proposedNextFireAt`, and win over the regular fire only when earlier; every proposal is labelled script-proposed in events and UI.
- **Consequences:** manual runs never queue behind a scheduled run (documented here so nobody "fixes" it silently); the queued-run path returns an honest skip for this fire rather than holding a wake-up for later — the reconcile pass re-runs missed fires under the misfire policy, which keeps behaviour bounded.

### ADR-044 — Press-button hardened as the archetype-A reference; `execution.min_interval_minutes` doubles as the proposal clamp
- **Context:** P4-15 wants the sample to demonstrate the scheduling contract end to end, and §11.7 says proposals are clamped to "the task's declared bounds (`min_interval`…)".
- **Decision:** `samples/press-button` now: emits evidence on the launch-failure path, proposes `ctx.next_run(after_minutes=5)` when the button is missing or the launch fails (best effort, ignored when the host has no schedule), and declares `execution.min_interval_minutes: 5` as that bound. The template copy under `app/src/main/assets/templates/press-button/` is refreshed in the same commit (ADR-038 pipeline).
- **Consequences:** `min_interval_minutes` keeps its existing schema meaning (manual cooldown hint) and gains the scheduler-clamp role — one field, documented in both places; no new top-level manifest key, so task.schema.json stays closed (`additionalProperties: false`).

### ADR-045 — Resume is a new attempt of the same run id; the state machine re-opens two rows
- **Context:** P5-05/P5-06 (§12.3): "Resume = a new `attempt` of the same run id, loading checkpoint and stage records." The state machine previously had no exit from `WAITING_USER`/`INTERRUPTED` back into the lifecycle.
- **Decision:** `RunStateMachine` allows `WAITING_USER → STARTING` and `INTERRUPTED → STARTING` (only). `RunOrchestrator.resume(runId, checkpoint)` re-issues a fresh run token, re-builds the RunSpec from the retained StartRequest, bumps the attempt and restarts the runtime; `FAILED`/`CANCELLED`/`SKIPPED` stay terminal (retry = new run). The original `StartRequest` is retained per run for exactly this purpose. The idle/heartbeat watchdogs treat the resumed attempt as a fresh baseline.
- **Consequences:** completed stages never repeat because the SDK skips `done` stage records from the checkpoint; `RunOrchestrator.resumeAfterInterrupt` is the CrashReconciler's entry point with the same semantics; History shows one row per run with an attempt counter instead of one row per attempt.

### ADR-046 — Stage records and on_resume live in the SDK; the host only persists what it is told
- **Context:** §12.2 wants stage records `{name, status, attempts, startedAt, endedAt, error}` with an in-progress marker and `verify/redo/manual` recovery, but the stage engine belongs to the script side (`autohost.flow`).
- **Decision:** `flow.stage(name, retries, on_resume, verify)` + `run_stages()` own the record lifecycle: the in-progress marker is durable (via `ctx.save()` → the host's checkpoint store) *before* the body runs; `done` stages never repeat; an interrupted stage follows `on_resume` — `verify` runs the task-provided postcondition (held → mark done, otherwise honest redo), `redo` always re-runs, `manual` raises `NeedsUser(STAGE_UNVERIFIED)`. Stage transitions are emitted as `stage_begin`/`stage_end` events carrying `{attempt, ok, error, verified}`; the host mirrors them into `stage_records` (RunPersistenceBridge). The old `StateProvider.stage_begin/stage_end` host-side markers are kept for compatibility but are no longer on the SDK's critical path.
- **Consequences:** Gate 5-a (3-stage task resumes without repeating stages) is provable in the SDK test suite on the JVM; the host never invents stage state; `ctx.once` stays for simple one-shot markers.

### ADR-047 — Checkpoints are atomic files under the run dir; `{"state": …}` is the canonical shape
- **Context:** P5-01: `ctx.save()` sends `{"state": {…}}` (the simulator and reference engine already agreed); the host's `StateProvider` expected `{"value": …}` — a real parity bug that would have failed every checkpoint on a device. Persistence also had to survive worker death.
- **Decision:** `StateProvider.set` accepts `state` (canonical) with `value` as a legacy alias, keeps a hot in-memory copy for the run, and mirrors every accepted write into `CheckpointStore`, which writes `<runDir>/checkpoint.json.tmp` → atomic rename (torn checkpoints impossible). AppGraph maps run id → `files/runs/<runId>/`. CrashReconciler restores the checkpoint from the DB row (RunPersistenceBridge mirrors the hot copy into `runs.checkpointJson`).
- **Consequences:** resume after `INTERRUPTED` restores exactly the last saved state; the file layout doubles as the retention sweep target; the parity invariant is now enforced by the shared SDK tests rather than by convention.

### ADR-048 — `ui.ask` blocks the worker call; prompts are notifications + a FLAG_SECURE dialog activity
- **Context:** P5-06 (§12.3): the run screen and a notification explain what to do; the script's `ui.ask` returns the answer. Workers are single-threaded from the script's view, so a blocking broker call is the natural WAITING_USER primitive.
- **Decision:** `UiPromptProvider` (`ui.prompt`) mints a prompt id, posts a heads-up notification (channel `prompts`, full-screen intent) and awaits a `CompletableDeferred` with `timeout_ms` (default 5 min, max 1 h). `PromptActivity` (not exported, `excludeFromRecents`, FLAG_SECURE per §14.4) renders confirm/text/choice and resolves the deferred; Dismiss answers `answered=false` honestly. Prompts are force-closed when the run goes terminal and by the kill switch. The run record flips to `WAITING_USER` only when the script *ends* with a `NeedsUser` outcome — a prompt inside a running script keeps `RUNNING` (the record shows the prompt stage).
- **Consequences:** Gate 5-b (round trip continues from the same stage) needs the resume path (ADR-045) plus the checkpoint, both of which exist; notification permission is already a required health row; the prompt surface never exposes input to the worker process directly.

### ADR-049 — Idle = no broker call and no non-heartbeat event; heartbeats never count as activity
- **Context:** P5-07 (§12.5): "the orchestrator tracks `lastActivityAt` (any broker call or emitted event)" — but worker heartbeats are emitted by a *host-side thread* every 2 s regardless of what the script is doing, so counting them would make the idle watchdog unreachable.
- **Decision:** activity = audited broker calls (the composite audit sink forwards them to `RunOrchestrator.onActivity`) plus every worker event **except `heartbeat`**. `IdleWatchdogPolicy` (pure) warns at 80 % of `execution.idle_timeout_seconds` (one warn event per run) and expires at 100 % → `finishRun(FAILED, "IDLE_TIMEOUT")` after killing the handle. Incidents (same task): `IncidentTracker` opens on a failed audited call (deduped per capability+method+stage+error), resolves on a later success in the same stage, and `closeRun` closes the rest at terminal; the tracker is fed from the same composite sink.
- **Consequences:** a wedged pure-Python loop is killed at its declared budget (Gate 5-e) while a legitimately long *broker* call keeps resetting the budget (documented limitation: a host-side wedge is the ReadGate/heartbeat problem, not idle); incidents surface on the Run screen and in the export bundle.

### ADR-050 — The authoring surface: line-delimited stdio MCP, spec-generated artifacts, drift-gated
- **Context:** P5-13..P5-16 (§5.6, §13.3, §5.5): a coding agent must drive the phone through MCP tools; the agent pack and capability catalog must be generated, never hand-written.
- **Decision:** `autohost mcp` is a stdio server speaking **newline-delimited JSON-RPC 2.0** (initialize / tools/list / tools/call; the 2024-11-05 stdio shape) with exactly the ten §5.6 tools wrapping the Dev API; Dev API errors become `isError` tool results. `tools/gen_artifacts.py` generates `docs/CAPABILITIES.md` + `autohost/_capabilities_gen.py` from `schemas/capability-specs.w1.json` with a `--check` drift gate (JUnit-free, in the Python suite). `autohost docs --pack` writes the Skill-format folder (`SKILL.md` + `references/` + `examples/`) from the same specs, adding live availability only when the device answers. MCP evals are YAML scenarios in `testing/mcp-evals/` driven by `tools/mcp_eval.py` against a scripted client (no phone needed).
- **Consequences:** Gate 5-f rehearses the inspect→write→run→debug loop on the PC; the recorder tools exist as typed `NOT_IMPLEMENTED` stubs so agents can probe for them (the overlay lands in Phase 6); regenerating artifacts is a recorded, test-enforced step (like the schedule vectors, ADR-039).

### ADR-051 — Flow v1 interpreter semantics (the executable contract is the Python reference)
- **Context:** P6-01..P6-05 (§7.9): the flow command set, modifiers, variables, expressions and error mapping needed one pinned semantics so the Kotlin `:runtime:flow` interpreter and the Python reference cannot drift. `schemas/flow.schema.json` constrains only the document shape, not the body details.
- **Decision:** `sdk-python/autohost_ref/flows.py` (pure stdlib, same pattern as the schedule reference, ADR-039) is the executable spec; `testing/golden/flow_vectors.json` (generated by `tools/gen_flow_vectors.py`, 44 cases) is the shared contract — every case pins the outcome, the exact broker call log (templated args, normalized wire selectors) and the event sequence, and the Kotlin `FlowInterpreterGoldenTest` replays it. Pinned semantics: modifiers live inside the command body; `timeout` is **seconds** (converted to ms for the broker; default 10 s); selector labels default to **eq** (precise by default, `mode` overrides; unresolved `${...}` stays literal and matches nothing); `when` keys AND-gate and skipped steps do not consume the run-wide step counter; `optional` swallows typed failures after the evidence event (never Cancelled/WaitUser); `retry.times` counts retries after the first attempt (matches SDK `flow.retry`), retryable failures only; `repeat.while` re-evaluates per iteration (false exits, non-boolean is INVALID_ARGS — fail closed); `runFlow` child env = parent copy, then the child's own env, then the explicit runFlow `env` (last wins), mutations stay in the child, result/next_run are run-global, depth cap 8; hooks: onFlowStart before the body, onFlowComplete after a successful body only; failure codes are broker error codes only (click verification failure = TIMEOUT/retryable; assertions = NOT_FOUND); `${secret.NAME}` resolves only in `inputText.text` / `setClipboard.text` with `secret: true` and is redacted in events; evidence events carry step/command/code/retryable/message/selector — the host attaches the compact dump + foreground at persistence, the interpreter makes no extra calls. Kotlin layout deviation: one `CommandExecutors.kt` instead of a per-command directory (single dispatch table, shared arg helpers); `SelectorResolver.kt` name kept per `docs/REPO_LAYOUT.md`.
- **Consequences:** regenerating `flow_vectors.json` requires a recorded decision (same rule as ADR-039); the Kotlin golden test is the compile-time catch-up for everything the Python suite already proves; the interpreter needs no Android types, so `:runtime:flow` is a pure JVM module.

### ADR-052 — Flow files are JSON in v1; YAML arrives with a real parser dependency
- **Context:** plan default 15 says flows are YAML (JSON accepted) parsed by "a vetted parser whose licence fits the app licence". The offline sessions have no Gradle/network, so adding a YAML dependency (snakeyaml / yamlkt) cannot be verified now, and hand-rolling YAML is exactly the kind of shortcut the plan forbids.
- **Decision:** `FlowParser.parse` accepts JSON text (and `fromJson` a parsed object) in Phase 6's first half. Tasks may carry `flow.json` today; the existing `press-button-flow` sample keeps its YAML `flow.yaml` and is loaded only once YAML lands (it uses YAML list syntax, which is not JSON). YAML support becomes a parser-plug change in `FlowRuntimeProvider` (P6-06) once a dependency (snakeyaml / yamlkt, licence-checked Apache-2.0) can actually be resolved on a machine with Gradle.
- **Consequences:** no silent YAML dialect: what is not supported fails with a precise parse error; the golden vectors store flow documents as JSON objects, so they are YAML-parser-independent; recorded in HANDOFF as a P6-06 prerequisite.

### ADR-053 — Recorded flows keep snapshots in a sidecar; the guard is an interpreter seam
- **Context:** P6-07/P6-08 (§7.9 recorder): plan says "each step stores a `pre_state` snapshot", but flow documents are schema-strict (unknown keys rejected, byte-identical parser errors) and must stay diffable — embedding recorder metadata would bend the authoring format and the Python reference for a device-only feature.
- **Decision:** the recorder emits **two files**: `flow.json` (schema-strict, every step carries an explicit `label` body modifier) and `<flow>.recording.json` (the sidecar: per-step `label`, `pre_state` (semantic `cls|id|text|desc` keys + package/activity), `needs_confirmation`, `selector_rank`, `elapsed_ms`, secret names; plus flow-level `on_mismatch` and `state_timeout_ms`). Guarded replay is a **Kotlin-only** interpreter seam: `FlowExec.stepGuard` (null = no-op — golden vectors unaffected) runs after a step's `when` gate and before execution; `GuardedReplay` implements it by polling `device.ui.snapshot` every 250 ms up to `state_timeout_ms`, comparing with `StateMatcher` (node-set Jaccard × 0.85 + package/activity × 0.15, threshold 0.85 **inclusive**), and applying `on_mismatch`: `stop` → `FlowFailure("PRE_STATE_MISMATCH")` with the score in the evidence (Gate 6-c), `ask_user` → WAITING_USER, `continue` → warn log + run. Steps without a sidecar entry are not guarded (hand-edited flows replay unguarded by design); a snapshot failure during polling counts as "cannot confirm", never as success. Password fields are recorded as `${secret.INPUT_n}` placeholders (`secret: true`) — recorded text never lands in a flow; the review screen tells the user to bind them in the profile.
- **Consequences:** the reference interpreter and `flow_vectors.json` stay recorder-free (the guard has no broker-visible semantics beyond the snapshot calls it makes); recorded labels make run logs and sidecar entries joinable; the sidecar is a new on-disk artifact the import pipeline ignores and the retention sweep can treat as part of the task folder.

### ADR-054 — Flows run in the main process; heartbeats come from a ticker, not the interpreter
- **Context:** P6-06: `RuntimeProvider.start` must return a `RunHandle` immediately, but a flow is just a coroutine — the orchestrator's lifecycle assumes a worker that emits heartbeats from a thread it controls (ADR-049: heartbeats prove liveness without counting as idle activity).
- **Decision:** `FlowRuntimeProvider` (type `flow`) resolves the document with `FlowSources` (manifest `runtime.entry`, else `flow.json`, then `flow.yaml` — ADR-052 order), then runs `FlowInterpreter` in a coroutine on the injected scope. Broker calls go through `BinderFlowBroker` (AIDL `call` → envelope decode → `BrokerCallException(code, message, retryable)`; scalar results wrapped `{"value": …}` like the sim adapter; blocking binder calls on the injected IO dispatcher). A **separate ticker coroutine** emits `heartbeat` events every 2 s, mirroring the Python worker's heartbeat thread: STARTING → RUNNING flips on the first heartbeat and heartbeat-loss detection keeps working even if the interpreter wedges inside a broker call; the interpreter's own inactivity is still bounded by the idle watchdog (broker calls are audited activity). Events are forwarded via the binder's `emit` without a `ts` (the orchestrator stamps arrival — one time source). A crashing interpreter is **worker death** (deathListener → INTERRUPTED), not a flow failure; a parse failure before start is `START_FAILED`. Pause gates between steps and inside sleeps (monotonic deadline, 50 ms slices); `kill` = cancel flag + job cancellation. Secrets stay an empty map until the `SecretsProvider` ships (it is a typed stub) — `${secret.NAME}` then fails `NOT_FOUND`, fail closed, same as today's Python tasks.
- **Consequences:** Gate 6-a's "no `:w*` process" holds for flows; both runtimes share token/grants/schedules/logging/evidence unchanged; the YAML plug (ADR-052) is one `YamlParserPlug.install(...)` line in `:app` wiring once the dependency resolves.

### ADR-055 — Phase 7 UI lives in `:app`; the handler contract, the Tier C sandbox and the console are events
- **Context:** Phase 7 (§10) adds the task-UI core: Tier B renderer, Tier C WebView host, imperative `ui.*`, and the handler path every surface shares. REPO_LAYOUT sketches `:feature:{taskui,surfaces,inspector}` modules; HANDOFF explicitly left the split-or-deviate choice open. Three more shapes needed pinning: how UI surfaces invoke task handlers (there is no run row for a button tap), what the Tier C sandbox enforces, and what `ui.console` *is*.
- **Decision:**
  1. **Placement deviation (owner-visible):** Phase 7 part-1 files live in `:app` (`taskui/`, `ui/taskui/`, `prompt/`, `notify/`, receiver) — the same practice Phases 5–6 already used for screens. A `:feature:` split without a compiling Gradle environment is refactor risk with no payoff yet; the split is re-evaluated at Phase 11 with a working build. REPO_LAYOUT marks the deviation.
  2. **Handler contract:** a UI-handler call is *not* a run — no Run row, no schedule lock, no checkpoint. The `:ui` worker process serves `IUiHandlerWorker.callHandler(spec, broker)`; the spec (`UiHandlerSpec`, mirrored by `autohost._runtime.run_ui_handler`) names the task, entry file and `@ui.handler`, carries config (never profile secrets — handlers get an empty profile) and a short-lived per-call run token built from the task's grants, revoked after the call. Single-flight per task (busy = refuse, never queue); **30 s cap** enforced on both sides (controller `withTimeoutOrNull` + worker deadline with cooperative `request_cancel` and a 3 s grace, then an honest `HANDLER_TIMEOUT`). Outcomes reuse the run-outcome shape; a handler must return a JSON dict (`HANDLER_RESULT` otherwise); a returned `"state"` key merges into the UI's `{{state.*}}` scope.
  3. **Tier C sandbox is host-enforced:** the WebView denies every non-`file:` request (403), refuses navigation off the bundle, serves only canonicalized paths under the task's own directory (404 otherwise), runs JS with content access/DOM storage/window opening off. The JS bridge object is constructed per task id — handlers of other tasks are unnameable. The page's strict CSP meta is author defense-in-depth, not the boundary.
  4. **`ui.console` is an event, not a capability:** `console.write` emits a redacted `ui.console` event on the normal event path (persisted with the run, visible in logview and run history). No new broker capability, no retention of its own.
  5. **v1 honest limits:** markdown renders as plain lines; the profile-picker widget is a pointer to the Profiles tab (real picker with the surfaces pass); declarative `state` starts empty per process (checkpoint-seeded state and live log streaming during runs land with part 2/policy pass); notification-action results are logged (the notification is the receipt).
- **Consequences:** the tracker's CAP-ui.prompt/CAP-notify.post rows close with evidence; Gate 7's Tier A/B/C sample requirement is satisfiable from the two new samples; `IUiHandlerWorker` is a new main↔worker AIDL surface the first build must generate; the `:feature:` deviation is recorded here instead of a module refactor.

### ADR-056 — System surfaces: one start path, honest FGS failures, prefs-backed bindings, and the gesture/inspector shapes
- **Context:** Phase 7 part 2 (§10.3): the bubble, five QS tiles, pinned shortcuts, the home widget, the token-guarded `RUN_TASK` intent, the inspector overlay and the volume-key stop all start runs or expose controls while AutoHost is backgrounded. Three shapes needed pinning: how surfaces start runs under Android 12+ background-FGS rules, where their settings live, and what the bubble/inspector v1s actually draw.
- **Decision:**
  1. **One start path:** every surface (tile, shortcut, widget, external intent, bubble-adjacent actions) calls `SurfaceRuns.start`, which goes through `AppGraph.startRun` with trigger `surface` (external intent: `external`) and a payload naming the entry point (`source: tile3|shortcut|widget|intent`). History and Dev API show where a run came from; no surface builds its own RunSpec.
  2. **Trampoline for launcher taps:** pinned-shortcut and widget Run buttons open `SurfaceRunActivity` (translucent, noHistory, excluded from recents), which starts the run and finishes — the FGS start rides a real user interaction. Tile clicks count as interactions too (`onClick`). If the system still refuses the FGS start (OEM-dependent), `RunForegroundService.start` now catches the failure and logs honestly — the run already exists and continues without the foreground notification; never a crash from the collector.
  3. **Surface settings live in `SurfacesPrefs`** (a SharedPreferences store, not the Room settings table): services/receivers read them synchronously on callback paths, they carry no secrets (the external token authorises *starting* runs only and rotates from the UI; it is not the Dev API token). Tile bindings are validated JSON per slot parsed by `TileBindings` in `:core:engine` (unit-tested, fail-closed). Widget task choice is a list of task ids; empty = all (first 5).
  4. **Bubble:** visibility is a pure policy (`BubblePolicy`): `auto` (default) shows while an active run is UI-acting — `AppGraph.startRun` records `uiActing` per run; `always`/`off` are the user override. The strip is a draggable `TYPE_ACCESSIBILITY_OVERLAY` added through the a11y service's window manager (no SYSTEM_ALERT_WINDOW grant, same mechanism as the recorder strip), with Open + Stop; Stop is `AppGraph.globalStop(reason)` — the §5.2 kill switch (notification action, bubble, volume-key gesture all land there; the orchestrator revokes tokens/kills workers and the terminal-transition collector closes prompts).
  5. **External trigger:** one exported receiver (`RunTaskReceiver`, action `app.autohost.RUN_TASK`), validated fail-closed by `ExternalRunRequest` in `:core:engine` — constant-time token compare, identifier-shaped fields, JSON-object payload; wrong token = dropped + `BAD_TOKEN`, logged, nothing started. `am broadcast` example shown in the Surfaces screen.
  6. **Inspector v1:** one full-screen a11y overlay drawing every node's bounds (labelled short-id/text) of the **live foreground package** (ForegroundTracker; AutoHost itself never drawn on) — a tap picks the deepest/smallest node under the point and copies `SelectorBuilder.forNode(...)` to the clipboard (preference order: resource-id → unique text → unique desc → class+index with a text-anchored parent → pkg+class; each candidate round-trips through `SelectorEngine`, so a copied selector is guaranteed to re-find the node it was copied from). While inspecting, the overlay absorbs touches — that is the explicit mode. "Add to recorder" stays a v3 item; the selector format is already the recorder's.
  7. **Volume-key stop ships off:** the a11y config has always declared `canRequestFilterKeyEvents`; part 2 adds `flagRequestFilterKeyEvents` and an `onKeyEvent` filter that consumes an armed DOWN (volume HUD stays quiet during the hold), schedules the hold threshold (default 1.5 s, 0.6–3 s configurable, Volume-Down by default) and fires the global stop exactly once while the key is still held; early release is a dead gesture. Pure state machine (`VolumeKeyHoldDetector`, unit-tested) + per-event config lookup (`SurfacesPrefs.keyFilterSpec`) so toggles apply without a service restart.
  8. **Widget:** Jetpack Glance per plan (dependency `androidx.glance:glance-appwidget:1.1.1`); one instance, up to 5 rows (task, last status from Room, Run button); refresh rides the run collector (throttled 1 s) plus explicit refreshes after surface starts.
- **Consequences:** `docs/ANDROID_MANIFEST.md` gains the 5 tile services, the widget receiver, the trampoline activity and the one exported receiver (token-guarded, per §14); the bubble/inspector follow the recorder-overlay honest-failure rule (denied overlay = logged no-op, never a crash); Gate 7-b/c/d/e are exercisable as written (tile/shortcut start runs; bubble Stop + volume-key halt a run over another app; inspector copies a working selector; RUN_TASK without token rejected); `SurfacesPrefs` is the second prefs store after the Dev API's — consolidation is a Phase 11 cleanup, not a redesign.

### ADR-057 — EventHub: one process-wide hub, sources where their service already lives, one FGS for the rest
- **Context:** plan §11.8 — most implicit broadcasts cannot be manifest-registered since API 26, so the hub must register receivers dynamically "inside a long-lived system-bound service (the Accessibility or Notification-listener service) when one is enabled, otherwise inside a low-priority foreground service that exists only while event triggers are armed". Three shapes needed pinning: where the hub object lives, which kinds ride which host service, and what the FGS actually is.
- **Decision:** the hub is a pure-JVM `EventHub` in `:core:engine` (fan-out by kind, self-unsubscribing subscribers, bounded 200-event ring buffer that `device.events.recent` reads). Android sources are split honestly by their host: **a11y-fed kinds** (`app.entered/exited` from ForegroundTracker transitions, `toast.shown` from the toast listener) are bridged in-process while the accessibility service is connected; **notification kinds** (`notification.posted/removed`) ride the P8-01 NotificationListenerService; everything else (`screen.on/off`, `user.present`, `power.*`, `battery.*`, `network.*`) is a dynamic receiver / `ConnectivityManager` callback inside a dedicated **low-priority `specialUse` FGS** (`EventHubService`) that exists exactly while an enabled rule uses a receiver-driven kind (`EventSourceCatalog.FGS_KINDS`) — started/stopped by `TriggerController.refresh()`, never permanent. Battery events are edge-triggered (level change → `battery.level`; crossing ≤15% → `battery.low`; recovering ≥25% → `battery.okay`, hysteresis). `network.wifi_ssid` carries the SSID only with fine location granted — otherwise the payload omits it and ssid-rules never match (documented, never faked). App-foreground events carry only the package name (§11.8 privacy); delivery to a rule is additionally gated on the target task holding the source's required grant (`device.events`; `device.notifications` for notification kinds) — §11.8 "event delivery is scoped to what the grant names".
- **Consequences:** no receivers in the manifest beyond the boot/alarm set (the FGS hosts them at runtime); the hub is unit-testable without Android; `triggers.catalog` and the Triggers UI render from `EventSourceCatalog` so a kind cannot be armed without documentation; `device.events.recent` is read-only by design — reactive delivery is trigger rules, not script subscriptions.

### ADR-058 — Trigger rules: guards are pure decisions, busy queues are in-memory, time sources share the schedule backends
- **Context:** plan §11.9 makes the trigger rule one data model for events and schedules with cooldown/debounce/busy-policy guards; Phase 4 stored and validated rules but armed nothing. The runtime had to decide where guards live (engine vs controller), how debounced bursts coalesce, and how `time.*` rules get armed without forking the scheduler.
- **Decision:** the guard chain (`max_launch_count → cooldown_seconds → debounce_ms`) is a pure engine object (`TriggerDecisionEngine`) over injectable inputs; the app-side `TriggerController` holds per-rule state (last fire, count, debounce hold, bounded busy queue) and applies the pure busy gate (`BusyGate`: `drop` default, `queue` bounded with **oldest dropped first**, `replace` = cancel the task's active runs then start). Debounce is a two-phase protocol: a matching event holds the latest payload and (re)starts the window; the deadline re-runs the full guard chain before firing (cooldown may have started meanwhile). `time.delay/absolute/daily/weekly` rules map through the existing `TriggerRule.toScheduleRule` (+ a `once` rule built for `time.delay`) and arm through the **same `SchedulerBackend` map as schedules** with a `trig-<ruleId>` fire id routed by `AlarmReceiver` — one arming model, one reconcile surface (app start, boot receiver, periodic ReconcileWorker). Fired runs carry trigger type `event` with `{rule_id, source, ...payload}`; `external` rules fire by name from the token-guarded `RUN_TASK` intent (`--es trigger <name>`), `triggers.test` (synthetic) and later webhooks; `task.chain` rules observe the run-terminal collector. Debounce holds and busy queues are **in-memory and honestly labelled as such** in the UI — a process restart drops queued events rather than pretending durability.
- **Consequences:** cooldown/debounce/busy behaviours are provable by unit tests (Gate 8-e); `triggers.status` reports live counters, cooldown remaining, busy depth and the grant gate; the schema's `queue_max` bounds the queue; Phase 4's "armed when the Phase 8 EventHub lands" note is now true.

### ADR-059 — Insecure-feature switches: pure policy in the broker, volatile snapshot, audit on every change
- **Context:** plan §14.5 — high-risk capabilities require the per-task grant AND a global switch, off by default, with a relaxed mode minus explicit denies; the pipeline comment reserved a link "between Scope and the provider" for exactly this.
- **Decision:** the policy (`InsecureFeatures`) lives in `:core:broker` (the broker cannot depend on the engine): a feature map (permission first — `device.app` mixes safe and dangerous methods — then capability id), `evaluate()` with deny-wins semantics, and a parser that drops unknown ids. Enforcement is `InsecureFeatureInterceptor` appended after `Scope` via the existing `BrokerService(interceptors=…)` hook; the failure is `INSECURE_FEATURE_DISABLED` with reason `DISABLED_BY_SETTING` and the `OPEN_INSECURE_SWITCH` fix (both pre-declared in schemas/errors.json). Persistence is three `app_settings` keys (relaxed flag, enabled set, denied set) behind `InsecureSwitchStore`, which keeps a **volatile snapshot** the interceptor's suspending lambda reads — the call hot path never touches the DB. Every change is audited as a WARN log under the `security` tag (switches are reachable only from Settings → Developer & security). `dev_api_remote` is in the KNOWN list now but enforced at the Dev API layer (part 2), not the broker.
- **Consequences:** Gate 8-b/8-c are exercisable (defaults off, deny wins, raw bridge gated by grant + switch when `android.api.direct` lands in part 2); low-risk capabilities are unmapped and never double-gated; the CompatReport wiring ("disabled by global setting") lands with the part-2 capability resolver pass.

### ADR-060 — `device.notifications`: the listener owns the actions, the bridge is the process seam, scoping is in the provider
- **Context:** plan §6.1 wave 2 — list/wait_for/read/press/reply/dismiss via a NotificationListenerService the user must enable; §11.8 scopes event delivery to what the grant names.
- **Decision:** a new `:capabilities:notifications` module follows the §6.3 template. `NotificationBridge` is the process-local seam (same pattern as `A11yBridge`): the active snapshot, a posted/removed SharedFlow for the EventHub, and **only sanitised fields** (key, package, title, text, subtext, big text, post time, ongoing, action labels) — never extras or content intents. The listener service publishes press/dismiss handlers into plain volatile slots on connect (only the listener may cancel notifications or send action PendingIntents); provider calls fail honestly when it is disconnected. Availability is the live listener connection (`NEEDS_SETUP` + `OPEN_NOTIFICATION_LISTENER_SETTINGS` fix otherwise); the health check reads the same bridge. Package scoping: the provider filters by the run's `device.notifications` grant packages when present — unrestricted grants see everything the listener holds, and the catalog says so. `wait_for` polls the bridge on a 200 ms cadence with a hard deadline (honest `TIMEOUT`), not a listener-side callback, so it works identically in tests.
- **Consequences:** the §6.3 checklist rows (spec, provider, availability, setup action, SDK, docs, tests, redaction posture) are all satisfied for the first wave-2 capability; `device.events`/`device.clipboard`/`device.intent` follow the same template in the same pass.


### ADR-061 — `net.server` webhooks: one localhost endpoint, token-mandatory, LAN opt-in is a settings toggle (not a §14.5 switch)
- **Context:** plan §6.1 catalog — "Local HTTP endpoint for webhooks → triggers. Localhost by default; LAN opt-in with token"; §14.5's switch list is frozen by ADR-059 and does not include a webhook-LAN entry.
- **Decision:** `:capabilities:net` hosts `WebhookServer` (a hand-rolled accept loop mirroring the Dev API server): `POST /hook/<name>` with `X-AutoHost-Token` fires the named `external` trigger rule through `TriggerController.externalFire`; everything else is 404/405/401 (bad tokens audited, bodies capped at 64 KB). The token is **mandatory in both bindings** — it is the only auth for the LAN case. The LAN toggle lives in Settings → Webhooks (S23) as a plain settings flag, deliberately outside the §14.5 switch list; app-side `WebhookController` owns lifecycle + the four `webhook.*` settings keys and reconciles at app start and on every toggle. The `net.server` capability is read-only for tasks (status + hook_names) — tasks never reconfigure the endpoint.
- **Consequences:** Gate 8-d's webhook-triggered run is a trigger rule away; the Dev API's `dev_api_remote` switch stays semantically separate (Dev API bind) from the webhook LAN toggle; the endpoint is off by default and leaves no trace when off.

### ADR-062 — `android.api.direct`: the broker handshake is the gate, the worker arms the passthroughs
- **Context:** plan §6.1 — "Direct Android API access from Python (jclass, system services). DANGEROUS; breaks the sandbox by design"; §18 P8 asks for an import guard with an on/off setting.
- **Decision:** the provider is deliberately small: `authorize` returns the worker marker only after GrantInterceptor (grant) and InsecureFeatureInterceptor (`raw_api` switch) passed — it re-checks nothing and adds no state. The **passthroughs live in the worker**: after a successful handshake the worker bridge arms `sys.modules['autohost.android'].__autohost_context__` (the Chaquopy Context) and `autohost.android.jclass` rides Chaquopy's `java` module; the SDK refuses both with `CapabilityUnavailable` until `authorize()` returned authorized (fail loudly). The **import guard** rides the Python scan: `raw_bridge_calls` flags Chaquopy imports (`java`, `com.chaquo.*`) and `autohost.android.{authorize,jclass,system_service}` calls; `ImportPipeline(rawBridgeGuard=true, the default)` refuses the import with `RAW_BRIDGE_UNDECLARED` unless `android.api.direct` is declared in `needs.capabilities`. The off setting is `raw_bridge_guard` in app_settings, owned by the Developer & security screen (audited like the switches).
- **Consequences:** Gate 8-c is two unit tests + the import-guard rule; the sandbox hole is exactly as wide as declared and never wider (no ambient context leak — the module global exists only after the handshake); the scan report carries `rawBridge` for the UI to show the offending files.

### ADR-063 — Lazy permission flows: FixHub routes every fix action, PermissionRequestActivity is the single request surface
- **Context:** plan §6.2 — availability reads `NEEDS_SETUP(RUNTIME_PERMISSION: …)` and the Fix button launches a small explanatory flow; the P2-19 leftover left the Health screen's Fix buttons wired to a no-op.
- **Decision:** a pure `LazyPermissions` map (capability → Android permission + kind + honest note) documents the expected asks up front; providers keep doing their own runtime checks (the `NEEDS_SETUP` reason stays the source of truth at call time). `:app/fix/FixHub` is the one place a fix-action string becomes an Intent (system settings screens, market, IME picker, in-app routes) — unknown actions return unrouteable instead of guessing. `PermissionRequestActivity` (transparent, excluded from recents) is the single surface for runtime-permission asks and the SAF folder pick: it requests exactly the named permissions, persists picked tree URIs (`takePersistableUriPermission`, `saf.last_tree` app setting for Permission Review), records outcomes in a process-wide `PermissionOutcomes` store, and finishes immediately. The run-terminal collector now also releases task-scoped power locks, closes ws handles and clears the run's overlays.
- **Consequences:** every typed fix action in schemas/errors.json now has a route; pre-flight re-checks stay provider-side (honest at run time); the fix flows are testable by intent construction without instrumentation.

### ADR-064 — The shell tier is our own ADB client; transports sit behind one `ShellTransport` seam
- **Context:** plan §3.1 T3 + default 7 — "our own ADB client — ADB-over-TCP first (the Android 10 path), Wireless-debugging pairing for API 30+, then Shizuku, then root (use a vetted OSS library if its licence allows)"; S4 asks to evaluate OSS ADB libraries.
- **Decision:** no AOSP code and no external ADB library — `AdbProtocol`/`AdbClient`/`AdbKeyStore` are clean-room pure Kotlin (24-byte framing, CNXN/AUTH handshake with the token→signature dance and one public-key offer, `shell,v2:` for separated streams + real exit codes with an honest legacy `shell:` fallback, binary-safe `stdoutBytes` for screencap). Every path implements `ShellTransport` (exec + memoized status) and the ordered `ShellTransports` holder picks the first live one: **adb-over-tcp → wireless pairing (draft, ADR-065) → Shizuku → root**. Shizuku ships via the Apache-2.0 `dev.rikka.shizuku:api` artifact, isolated to `app/shell/ShizukuProcessExec.kt` so `:capabilities:shell` and its JVM tests stay dependency-free. ADB keys are one persisted device identity under `filesDir/adb`.
- **Consequences:** one connection per exec keeps the client stateless (honest about latency; the shell tier is the power path, not the hot one); the fake-adbd tests run on real loopback sockets per the repo's fakes rule; a per-boot `adb tcpip 5555` remains the Android 10 ritual (the post-reboot reminder lands in part 2); adding a transport never touches the providers.

### ADR-065 — Wireless-debugging pairing is honest-draft until hardware verification
- **Context:** plan §3.5 labels API 30+ paths UNVERIFIED-on-hardware until run; the AOSP pairing protocol (SPAKE2 inside a TLS-PSK channel) cannot be byte-confirmed against a real Android 11+ host from the build sandbox.
- **Decision:** the SPAKE2 core follows **RFC 9382 exactly** (P-256-SHA256-HKDF-HMAC) and is pinned in tests to the official Appendix-B vector (pA byte-exact) plus a full two-party transcript cross-generated by an independent Python implementation (`scripts/spake2_ref.py`) — the crypto is trusted, the wire is not. The TLS-PSK channel sits behind a `PskTlsChannel` seam whose default factory probes installed security providers for PSK support (Conscrypt on device; plain JVM = none). `WirelessPairingTransport` implements the pairing flow (code → SPAKE2 → key exchange) but reports `Unsupported(TLS_PSK_PROVIDER_MISSING)` or `Unsupported(WIRELESS_PAIRING_DRAFT)` — never a fake success — until Gate-9 device work either verifies the framing against a real host or fixes the bytes.
- **Consequences:** the Android 10 phone (the primary device) is unaffected — its path is ADB-over-TCP; the Setup flow presents wireless pairing only as advanced/draft on API 30+; the SPAKE2 core is reusable as-is if the framing needs adjustments.

### ADR-066 — The `device.shell` allowlist is fail-closed with an unconditional metacharacter deny
- **Context:** plan §6.1 — "DANGEROUS; allowlist default empty"; §14.5 makes `device.shell` two-level gated (grant + `shell` switch); the `shell:` service runs commands through `/bin/sh`, so a single overly-broad pattern could become arbitrary shell.
- **Decision:** the grant scope is `{"commands": [patterns]}`: **missing grant → PERMISSION_DENIED; empty list → deny-all; `*` (any run) and `?` (one non-space) globs** — all evaluated in the pure `CommandAllowlist` before any transport I/O, and mirrored by the sim so SDK tests pin the same semantics. Shell metacharacters (`; & | \` ( ) < > newline` and `$`) are refused **even when a pattern would otherwise match** — v1 has no use case for them and they defeat pattern review; the 4000-char cap bounds injection surface. `set_text(secret=true)` through the ShellUiProvider is refused with `TEXT_INPUT_REJECTED` (the text would ride the command line where evidence redaction cannot reliably reach) — secrets go through `device.ime`. Internal provider commands (uiautomator dump, screencap, input …) do not pass the task allowlist: they belong to the `device.ui`/`device.screenshot` grants and are part of those capabilities' contracts.
- **Consequences:** `device.shell` is reviewable at grant time (a human can read the whole pattern list and know exactly what can run); relaxing metacharacters later is a deliberate, audited change to one pure class; the provider's typed errors (`SCOPE_VIOLATION` + `OPEN_PERMISSION_REVIEW`) match the grant-review flow.

### ADR-067 — The `device.settings` write path is one door with a protected-key denylist
- **Context:** plan §6.1 — "Read system settings; write via Write-settings or secure settings; write is gated" (W4). Two write paths exist: the one-time `WRITE_SECURE_SETTINGS` grant (PC helper `autohost grant-secure-settings`) and the paired shell tier (`settings put`); tasks must never be able to break the self-heal machinery that depends on the same keys.
- **Decision:** one `SecureSettingsHelper` (app layer) owns every settings write — direct `Settings.X.put…` when the grant is held, shell `settings put` through the first live transport otherwise — and the `device.settings` provider exposes it as a `write` method behind the `device.settings.write` permission with the pure `SettingsWritePolicy`: **protected keys are always refused from tasks** (`enabled_accessibility_services`, `accessibility_enabled`, `default_input_method`, provisioning keys — self-heal owns them and writes them through the helper, deliberately outside the task-reachable policy), `secure`/`global` tables need `confirm:true`, values are capped at 1000 chars with control characters refused. Writes verify by read-back and report `{written, path: 'write_secure'|'shell', verified}`.
- **Consequences:** the asymmetry is the point — a task cannot disable the a11y service or swap the IME, while self-heal can; auditing writes is one log tag; the P4-14 boot heal keeps its direct path and gains the shell fallback through the same door.

### ADR-068 — The UiAutomation provider is experimental, exclusive, and the only secret-safe shell-tier text path
- **Context:** plan §5.4 — "a provider built on the UiAutomation connection suppresses ordinary accessibility services; A11yProvider and UiAutomationProvider are mutually exclusive; the broker never activates both"; S4/G9-e records the real behaviour.
- **Decision:** the session is an `Instrumentation` runner (`app/shell/UiAutomationRunner`) spawned through the shell tier with `am instrument` (no `-w`) that serves a line-JSON protocol on a loopback socket (dump as uiautomator-shaped XML, click/text/gesture/key/screenshot); the pure `UiAutomationExclusivity` policy decides: **start refuses while the a11y service is connected or the experimental toggle is off; a live session closes itself the moment the service reconnects** (the service always wins). The provider registers BETWEEN a11y and `shell.uiautomator`, so first-available resolves the chain naturally and `availability()` reports `Unsupported(UI_AUTOMATION_SESSION_DOWN)` rather than setup UX. `set_text(secret:true)` is ALLOWED here — the text rides the loopback socket into the app's own instrumentation process (never a shell command line) and goes through `ACTION_SET_TEXT`; this is the honest counterpart to ADR-066's refusal. Everything device-touching is UNVERIFIED-on-hardware until Gate-9.
- **Consequences:** the experimental toggle lives in Settings → Shell tier (not an insecure-feature switch — plan §14.5 did not pre-declare one, and exclusivity is enforced in code, not by a permission); the runner stays dumb (loopback, one client, quit op) so the policy surface is testable; if S4 shows the phone does not suppress a11y the exclusivity rule still stands (cheaper than re-verify per build).

### ADR-069 — `device.app.manage` is confirm-railed, and installer auto-accept reports UI-chain outcomes, never package claims
- **Context:** plan §6.1 — "Install/uninstall APK, clear data, grant/revoke permissions; T3; DANGEROUS" + the risk table's "Auto-accept of system dialogs breaks on OEM dialog variants" mitigation (view-id + localized-label matching, cooldown, fallback to WAITING_USER).
- **Decision:** destructive methods (`clear_state`, `install`, `uninstall`) demand an explicit `confirm:true` (SCOPE_VIOLATION otherwise — an accidental `pm clear` must never be one forgotten flag away); `force_stop` runs the verified chain (shell `am force-stop` with a real exit code → the T1 App-info UI path → `killBackgroundProcesses`, VERIFIED/BEST_EFFORT/FAILED honestly); `pm grant/revoke` report `verified:false` (no readback claim). The installer-UI path fires ACTION_VIEW through FileProvider with `AutoAcceptPolicy.Flow.INSTALL` pending (the existing gate's cooldown/rate/give-up machinery; new `PACKAGE_INSTALLER_CONFIRM` dialog ids across AOSP/OEM variants + a flow-dialog affinity so a projection flow can never tap an installer button); outcomes are `CONFIRMED` (the installer window appeared and left) / `WAITING_USER` (nothing we recognize appeared in time) / `FAILED` (path unreadable by the app) — **never a package-manager readback claim**.
- **Consequences:** `pm install` (VERIFIED on Success) is the default path; the installer mode is the a11y-only fallback; OEM variants that defeat the id/label list degrade to WAITING_USER, which the spec documents as a first-class result; Gate-9 device work records the real dialog shapes.

### ADR-070 — The browser tier is three providers behind one gate chain, challenges route to WAITING_USER by construction, and the WebView is never stealth
- **Context:** plan §6.1 browser row — "Automate pages in a visible in-app WebView with real input events; drive the user's real browser through T1; optional CDP via T3. No stealth features; challenges ⇒ `WAITING_USER`" — plus Gate 10-c ("never bypassed") and the risk row "the Android 10 phone … has an old WebView".
- **Decision:** one `browser` capability family (`browser.webview` T0, `browser.a11y` T1, `browser.cdp` T3 draft) behind ONE pure gate chain (`BrowserPolicy`: the exact NetPolicy domain semantics on the grant scope, http/https + the `task:<bundle-relpath>` scheme only — never `file:`/`javascript:`/`data:`, and a `..`-refusing bundle-path guard). Challenge detection is a pure engine over URL/title/visible-text markers; a detected wall rides the result as `challenge:{kind,matched}` and the **SDK raises NeedsUser(SECURITY_CHALLENGE) by default** — there is no solving, retrying or bypassing path in the module; `challenge:"report"` only lets a script observe the verdict. Input honesty is on the wire: every act result carries `input_mode` (`real` injected MotionEvents/KeyCharacterMap key events, `synthetic` JS fallback the S25 spike may force on old WebViews, `a11y`, `cdp`) and a synthetic input is never claimed trusted. The webview surface is a visible activity with a Close strip (back = close through the controller), per-profile cookie isolation via `setDataDirectorySuffix` with a process-wide profile lock (CookieManager state is process-global — parallel cross-profile pages serialize, never silently share). The a11y link refuses cookies/CSS/URL-claims outright (`COOKIES_UNSUPPORTED_LINK`) instead of approximating them. Page cap: 4 per run; text is never echoed from `type`.
- **Consequences:** Gate 10-a can run fully local (`task:` pages need no network grant); S25/S26 measure the two honest fallbacks at the phone without touching providers; the browser module stays pure JVM (host seams injected from AppGraph per the ADR-035 lambda pattern).

### ADR-071 — CDP runs over a local adbd forward through the paired shell tier, draft until S27
- **Context:** plan §18 P10 "CDP over an ADB stream" + the shell tier being the established T3 door (P9) + the wireless-pairing draft discipline (ADR-065).
- **Decision:** `browser.cdp` reaches a devtools endpoint with `adb forward tcp:<p> localabstract:<socket>` **executed through our own shell transport** (adbd is already trusted there), then plain HTTP `GET /json/list` and an RFC 6455 WebSocket to the target — the P8-08 `JvmWsSocketFactory` does socket+handshake, a ~60-line client-frame codec in `:app` does text frames (the net module keeps its framing private). The pure `CdpClient` (kotlinx.serialization JSON, id-correlation, event skipping) knows the protocol; the provider owns route, URL allowlist (same BrowserPolicy), run-scoped teardown (`adb forward --remove` on run-terminal). `status` reports `verified_on_hardware:false` with the S27 note until the spike measures both routes (our debuggable WebView, the user's Chrome).
- **Consequences:** no new module dependencies (browser stays core-only); a route failure degrades to honest NEEDS_SETUP/UNSUPPORTED, and the fallback is browser.a11y for the user's browser — never a raw-socket side door.

### ADR-072 — Vision engines are seam-isolated: bundled ML Kit OCR + ZXing QR (both Apache-2.0) and a pure-Kotlin NCC template matcher; results are hints on the wire
- **Context:** plan §6.1 vision row — "OCR, template match, QR decode; T4; Hints, not proof" — plus the clean-room licence rule (Apache/MIT only) and the S28 latency question on a 32-bit low-RAM phone.
- **Decision:** `OcrEngine`/`QrDecoder` are interfaces; the module wraps `com.google.mlkit:text-recognition` (bundled, no Play Services) and `com.google.zxing:core` — the ONLY two touchpoints, both Apache-2.0, recorded in VERSIONS/THIRD_PARTY_NOTICES. Template match is a dependency-free zero-mean NCC (grayscale BT.601, coarse stride + refine, thread-safe per-call needle prep) — JVM-testable with deterministic golden vectors, no OpenCV APK-weight. Every provider result carries `hint:true` on the wire; OCR text may contain secrets so results are never auto-evidenced (script decides, as with logcat); image access is confined to the screenshot chain + run/task-scoped paths with canonical-path containment.
- **Consequences:** S28 can swap engines without touching the provider; the pure matcher's cost is measured at the phone with adaptive stride as the documented fallback; "hints, not proof" is enforced by the payload shape, not just prose.

### ADR-073 — The personal-data and hardware clusters are seam-backed, row/byte-capped, and honest about lazy permissions and background location
- **Context:** plan §6.1 W3 rows — contacts/calendar/media ("Query/insert; lazily requested runtime permissions"), location ("Background location needs an extra grant"), camera/microphone/sensors ("Permissions; background limits") — plus the P8-14 lazy-permission machinery that must now carry real asks.
- **Decision:** one `:capabilities:data` module; every provider is a pure gate over a seam (`PersonalDataStores`/`HardwareSeams`) with the Android half in `:app/data/*` (ContentResolver/MediaStore, LocationManager one-shot with listener cleanup, legacy Camera one-shot with a visible shutter, MediaRecorder bounded AAC, SensorManager one-shot latch) — the module stays JVM-testable and base64 lives in the seam (never android.util in the providers). Caps are policy constants, not folklore: rows 1..500, calendar windows ≤31 days, media reads/inserts ≤10 MB, recordings 500..60 000 ms, sensor samples bounded one-shot (no streams). Availability is the lazy-permission truth (`RUNTIME_PERMISSION:<id>` + REQUEST_PERMISSIONS) refreshed from the app via `refreshDataPermissionState()`; `location.last_known` on a background-only run is NEEDS_SETUP(BACKGROUND_LOCATION) — never a silent stale-fix downgrade (stale fixes are marked `stale:true` even when served). Sensors need no permission and read one-shot samples only.
- **Consequences:** the app-side files are the only Android surface to verify at the phone; caps and permission gates are testable without a device; a future trigger-rule "sensor stream" capability extends the seam instead of reopening providers.

### ADR-074 — SMS/telephony are full-flavor, switch-gated, money-railed, and never claim delivery or connection
- **Context:** plan §6.1 device.sms/device.telephony ("Dangerous; restricted for sideloaded apps; `full` flavor only"; W3) + the §14.5 switch list that already named `sms` and `telephony` + §0.4 (never cost the user money invisibly).
- **Decision:** both providers subclass a flavor gate: on `core` the manifest declares no SMS/call permissions, so availability is honest `UNSUPPORTED_FLAVOR`; on `full` the two-level gate (grant + `sms`/`telephony` switch, enforced upstream by InsecureFeatureInterceptor) applies. Sends ride DataPolicy rails: destination validation (digits/separators, E.164 length), explicit premium-rate refusal (`19xx`/`0900`), short codes refused unless `allow_short:true`, body ≤480 chars/≤3 parts, per-run budget of 10 sends (static run-keyed counter, cleared at run-terminal). Outcomes are honest on the wire: `sent` is the radio accept, `delivered` is ALWAYS false (receipts are a carrier promise), `place_call` is ACTION_CALL through the dialer with `verified:false` (the user sees and can cancel it). Reads are sender-scoped by the grant's `senders` list via `ctx.scopePackages`.
- **Consequences:** a task can automate verification-code flows (read_inbox/wait_for) but cannot silently message premium numbers; the flavor story matches the manifest split and the risk table's sideload honesty.

### ADR-075 — net.socket is a domain-gated initiator; net.reverse dials out with the token in the first frame, never the URL
- **Context:** plan §6.1 `net.socket` (TCP/UDP, W3) and §6.5 `net.reverse` ("Device-initiated WebSocket to a host; off by default; token + TLS") — the last W3 wave items.
- **Decision:** `net.socket` reuses the exact NetPolicy domain semantics on its grant scope, caps payloads (5 MB TCP / 65 527-byte UDP ceiling), keeps ≤8 run-scoped TCP handles (closed at run-terminal like the ws handles), and offers only INITIATION (tcp_connect/send/recv/close + one-shot udp_send/udp_recv) — listeners stay `net.server`'s job. `net.reverse` is the device-initiated control/reporting WS: the token is sent as the FIRST frame (never a URL parameter — URLs are logged), plain ws:// is localhost-only (wss:// required for remote hosts — token + TLS as the plan spells), and the family is switch-gated by a new `net_reverse` entry in InsecureFeatures.KNOWN/featureFor (off by default; enforced upstream by the interceptor — the provider never checks the switch itself). Handles are run-scoped and torn down at run-terminal.
- **Consequences:** a PC can drive/report through an outbound connection with no USB and no listening socket on the device; the Dev API's reverse transport (Phase 11) can ride this seam; the switch keeps the feature dark until the user flips it.

### ADR-076 — The JavaScript runtime is in-process QuickJS behind a pure `JsEngine` seam, with ONE bridge op table and a deliberately small v1 surface
- **Context:** plan §17 Phase 11 ("JavaScript (QuickJS) runtime over the same broker") and §21 default 9; Gate 11 F2 (three runtimes coexist) and F5 (all through the same broker). The manifest schema and `ManifestValidator` already accepted `runtime.type: "javascript"` with `.js` entries since P2.
- **Decision:** `:runtime:js` is **pure JVM** (like `:runtime:flow`): `JsRuntimeProvider` runs one QuickJS engine instance per run on a dedicated daemon thread (script evaluation blocks; a dispatcher pool thread must never be pinned), one heartbeat coroutine, the same `finished`-event contract, worker-death on engine-internal crash. The binding (`io.github.dokar3:quickjs-kt-android` 1.0.x, Apache-2.0) is touched by exactly ONE owner-verified file — `app/runtimejs/QuickJsEngineFactory.kt` (the ShizukuProcessExec/MlKit isolation pattern). The JS surface is the shared `prelude.js` resource over ONE engine global `__autohost_bridge(frame)` with a single-arg `[op, payloadJson]` frame; the op table (call/emit/sleep/ctx/state_save/secret/clock/result/next_run/capabilities) is documented in `docs/SDK_JS.md` and pinned by JVM tests (JsBridgeTest) AND sim tests (test_p11_part1) from the JS side. Blocking semantics match the Python SDK (calls park on pause, cancel raises at the next call/sleep). Caps come from `JsRunPolicy` (32/16 MB heap by RAM class, 1 MB stack, deadline = the manifest's `timeout_minutes`) enforced by the engine's interrupt watcher; an in-process runtime cannot be force-killed like a worker process — kill() drives the interrupt handler and a run wedged inside one broker call unwinds when that call returns (honest limitation, bounded by caps). JS v1 keeps the surface small on purpose: `autohost.call` (the universal broker verb, spec-locked) + client-side helpers (sel/log/ctx/KV/evidence/errors) — rich per-module ergonomics can ship later without runtime changes. Secrets stay fail-closed (NOT_FOUND) exactly like flows and Python today.
- **Consequences:** Gate F5 is structural (the JS bridge speaks the same envelope protocol through the same binder); the QuickJS binding's exact API is verified at the first Gradle build in one file; JS tasks are ESM (`export function main()`), with `./lib/*.js` imports served by a containment-checked module loader (and node's require-of-ESM in the sim).

### ADR-077 — The simulator runs real JS tasks under node with the SAME prelude; the Python host serves the same op table and classifies branch-for-branch like `execute_with_runtime`
- **Context:** plan §19 layer 5 (Python SDK tests + sim run in CI without a phone) — the JS runtime needs the same sandbox story, and no JS engine exists in the sandbox beyond node.
- **Decision:** `autohost_sim/js_host.py` spawns `node node_shim.cjs <prelude.js> <entry.js>`; the shim is a dumb stdio transport (one JSON line per request/reply) that evaluates the byte-identical prelude copy, loads the entry (ESM via node's require-of-ESM + syntax detection, plain scripts via `vm.runInThisContext`), and forwards every bridge frame. The Python host serves the ops over a real `Runtime` (SimTransport), so config, secrets, redaction, cancellation and capability dispatch behave exactly like Python task runs, and the outcome classification mirrors `execute_with_runtime` branch-for-branch (ok/cancelled/needs_user/autohost/entry/exception, traceback riding FAILED:EXCEPTION). A byte-identity drift test pins the two prelude copies together; a sel-parity test pins the prelude's JS selector builders against the Python SDK's `sel` module output for a 18-builder matrix. Runs skip when node is absent; a 120 s host deadline bounds a wedged shim.
- **Consequences:** the sim can sim-prove Gate 11 F2/F5 with real JS task code (not a mock), and any drift between the device bridge (Kotlin) and the sim host (Python) is caught by the mirrored test matrices rather than by a phone.

### ADR-078 — The task repository is a pure v1 index + select policy; fetching stays the caller's job until the Task Studio/CLI lands
- **Context:** plan §17 Phase 11 "task repository/index import" and Gate 11 F1 (a brand-new task installed, profiled, scheduled). Bundles and the import pipeline (P2) already exist; what was missing is the catalog layer.
- **Decision:** `core/engine` gains `RepoIndex` (pure, JVM-testable): `index.json` v1 (`schema`, `name`, `updated_at`, `tasks[]` with `id`/strict-semver `version`/`source` (local path or https URL — never fetched here)/optional `title`,`runtime`,`sha256` (64-hex),`min_host_api`,`notes`; unknown keys rejected, duplicate ids keep the first occurrence with a typed issue) and `select()` verdicts (Install / Upgrade(from,to) / UpToDate / Reject(HOST_TOO_OLD|REPO_OLDER) — downgrades need an explicit uninstall, exactly like the removal policy's confirm rail). `verifySha(expected, actual)` is the integrity check for callers that fetched a bundle. The fetching UI, the CLI verbs and the Dev API wiring are Phase 11 part 2 (Task Studio) work — this ADR only fixes the data contract and the decisions.
- **Consequences:** the index format is frozen before any UI leans on it; Task Studio/CLI become thin consumers; a repo cannot silently downgrade or bypass the host-API gate.

### ADR-079 — Plugins contribute capabilities through ONE validated AIDL contract; the host parses and gates EVERYTHING
- **Context:** plan §18 P11 "plugin APK SDK + one example external capability plugin" (Gate F4: a plugin is used by two tasks with zero task changes). External code must join the broker without widening the trust boundary that the interceptor chain enforces.
- **Decision:** `plugin-sdk` ships the `ICapabilityProvider` AIDL (`apiLevel` / `describe` / `availability(envJson)` / `invoke(callJson)`) plus a dependency-free base service; `core/engine/plugins/PluginHost` (pure) owns the policy: the api band (currently 1..1), a fail-closed `describe()` parse (`plugin.*`-namespaced capability ids only, snake_case method names, one permission per method, unknown keys rejected, ONE malformed entry rejects the WHOLE plugin — a half-registered plugin would look available and fail at call time), host-collision refusal (a plugin can never shadow or chain onto a host capability), and typed envelope handling (`PLUGIN_ENVELOPE_MALFORMED`, availability parse failures → `Unsupported`, never a crash). Discovery rides the package manager with the `app.autohost.plugin.CAPABILITY_PROVIDER` intent action (the host manifest declares a matching `<queries>` entry); `app/plugins/PluginController` only moves bytes and manages bindings. Grants resolve because the attach result carries a permission fragment merged into a NEW immutable `PermissionIndex.mergedWith(...)` — host mappings always win, plugin fragments never shadow. Live grant machinery: `AppGraph.attachPluginPermissions` swaps the volatile index + rebuilds GrantBuilder/GrantService (runs in flight keep their built grants; a DataGraph initialized before attach keeps the display-side GrantService — recorded, display-only).
- **Consequences:** the example plugin (`samples/plugin-example`, a standalone gradle project) proves F4 without host code changes; a malicious plugin is bounded to the JSON contract (its own failures are typed, availability is honest); the AIDL/ServiceConnection half is UNVERIFIED-on-hardware until a real plugin APK is installed (the pure host contract is fully JVM-tested).

### ADR-080 — App packs ride the RUN CONFIG (`config.packs`): one mechanism for all three runtimes, version-pinned per run
- **Context:** plan §7.10 — `.aapack` = named selectors, Screen signatures, locale labels and tips for one target package, referenced from tasks (`uses_packs`) so a fix ships once for every task. The runtime mechanism was unspecified; the candidates were a new broker capability, staged files in run dirs, or the run config.
- **Decision:** the host resolves `uses_packs` at run start (pure `AppPacks.resolve` against the installed packs, in task order, missing packs warned honestly) and injects the payload into the run config under the reserved key `packs` — `ctx.config` for Python, the same config op for the JS prelude, `{{config.packs.*}}` for flows. No new broker surface, no file IO in workers, deterministic per run, and the pack version that was actually used rides the run result for evidence. A user-defined config key named `packs` colliding with the reserved key logs a warning and the HOST value wins (the reserved key is not user surface). Pack documents (`pack.json` v1) parse fail-closed (`AppPacks.parse`: reverse-DNS id, android target, strict semver, snake_case selector/screen names, BCP-47 label tags, tips cap); named selectors are selector DOCUMENTS (the `sel.to_json()` shape — ONE selector language for flows, packs and the SDK), rebuilt for Python/JS via the new public `autohost.sel.from_json`. Labels fall back exact tag → language-only tag → `en` → first available, mirrored exactly in the SDK helper. `.aapack` install is `PackController` (zip → parse → store under `filesDir/packs/<id>/<version>/`, zip-slip rejected); the import pipeline emits non-blocking `PACK_MISSING` warnings when the device cannot resolve a referenced pack, and run-start injection stays the honest gate.
- **Consequences:** the SDK gained `autohost/packs.py` (+stub, exports) with `PackMissing`/`SelectorMissing` typed errors — a missing pack is an honest FAILED run, never a silent fallback to a hardcoded selector; the sim mirrors the injection (`resolve_packs`) for all three run hosts; flows read packs only through `{{config.packs.*}}` paths (the frozen v1 command set gains no pack verb).

### ADR-081 — The reverse Dev API transport dials OUT; the token rides the FIRST frame, never a URL
- **Context:** plan §18 P11 "reverse WebSocket transport". The Dev API is localhost/adb-forward by default; phones without USB attached need the same token-gated JSON-RPC surface over the network, device-initiated (rides the ADR-075 `net.reverse` convention).
- **Decision:** the PHONE is the WS client: `core/devapi/ReverseDevApiLink` (pure JVM) dials `ws://<pc>:<port>/reverse`, performs the RFC 6455 client handshake (verifying the Accept value), sends `{"token": "…"}` as its FIRST frame, then serves the SAME `dispatch()` the HTTP server uses (caller `"reverse"`, Bearer token in-band, so the token check + rate limiter apply unchanged) — requests flow PC→phone, one text frame per response (64-bit lengths; 8 MiB decode cap). `WsFrames` is the shared pure codec (both roles, mask-expectation enforced, RFC 6455 §1.3 accept vector pinned in tests). The PC side is `autohost bridge` (WS server role + first-frame token validation + a localhost HTTP proxy on 8081 so the existing CLI/MCP tooling works unchanged); its relay is deliberately single-reader (the first draft had a reader loop racing the relay for the response frame — fixed and documented). The app's `ReverseLinkController` dials with bounded backoff, is gated on the Dev API being enabled, and reports honest state/lastError (Settings → Developer → Reverse bridge, S26a). No new insecure switch: reverse IS the dev api (same token, same router); it is opt-in per session by construction (a URL must be entered).
- **Consequences:** no USB, no adb forward needed for agent sessions on the LAN; the bridge proxy keeps `autohost --port 8081` semantics identical to the localhost server; a wrong token is refused with a counter (auth_failures) and BRIDGE_DOWN surfaces honestly through the proxy.

### ADR-082 — Backups carry secrets as NAMES only; restore re-asks by design
- **Context:** plan §18 P11 "backup/restore (tasks + profiles minus secrets)" and §21-13 "secrets never exported". The trap: a backup that includes values is a leak; a backup that loses profiles is useless.
- **Decision:** `core/engine/backup/BackupCodec` (pure) defines document v1: tasks (manifest verbatim + bundle sha + `bundle_b64` when the bundle exists — dev-folder tasks export without one and the restore plan says so honestly, since a manifest alone cannot resurrect code) and profiles (values + `secret_names` ONLY). Secrets are excluded BY CONSTRUCTION and the codec defends it from both sides: encode refuses profile values that contain secret-shaped keys; decode REFUSES any document carrying `secrets`/`secret_blobs`/`secret_values`/`ciphertext` anywhere (a hand-edited or third-party backup cannot smuggle values in). Restore planning is pure (RESTORE_NEW / OVERWRITE-only-when-confirmed / SKIP; profiles RESTORE_NEW with the names listed for re-entry, SKIP_EXISTS on id collision); the app `BackupController` applies tasks through the SAME review→install pipeline (source "backup") and re-creates profiles with EMPTY secret stores (stale blobs wiped via `deleteForProfile`). SAF export/restore in Settings (S26); no secrets ever touch the export path.
- **Consequences:** the backup file is safe to store and share but never sufficient alone — that asymmetry is the feature; upgrade/migration of the backup format rides the `schema` field with the same gate rules as task manifests.

### ADR-083 — The Task Studio edits DEV-FOLDER tasks through the importer's own validator; installed bundles are never hand-edited
- **Context:** plan §18 P11 "in-app Task Studio". Two editing surfaces exist (dev-folder drafts and installed bundles); editing installed bundles would bypass the import pipeline's hash/report/grants story.
- **Decision:** `StudioDraft` (pure) holds the editable fields + entry text, builds the manifest by overlaying edits on the ORIGINAL JSON (unchanged fields survive verbatim), and validates through `ManifestValidator` — the Studio cannot produce a bundle the importer would refuse (including the `uses_packs` top-level key). The app screen (S27) creates dev-folder tasks from per-runtime templates, saves to `dev/<id>/task.json` + entry file, and validates on save; the repo tab is P11-03's consumer (https/file only, RepoIndex verdicts, sha-verified install through the standard review→install path). Installed tasks are edited by re-import — the honest round trip that keeps hashes, reports and grant diffs intact.
- **Consequences:** no editor drift between Studio and imports (one validator); the host API level reported to repo entries lives in ONE place (`StudioController.HOST_API`, currently 8 — bumped with recorded ADRs); PC-side `autohost repo` mirrors the index rules for parity (pinned by tests on both sides).

### ADR-084 — Verification ticks follow evidence, not cross-phase gate ordering
- **Context:** the verification epoch must record sandbox-runnable and module-level results immediately, while early real-device gates may remain open until the owner can perform the phone procedures. Root `AGENTS.md`, `docs/PROGRESS.md`, and `tools/progress.py` previously treated gate order as a restriction on tracker ticks, so a later independently verified task could not be recorded despite having its required evidence.
- **Decision:** phase ordering continues to constrain starting new implementation scope, but it does not constrain verification status for work already written. Tick each independently passed task when its required evidence is recorded, regardless of earlier open gates. A gate itself remains unticked until its exact procedure and evidence are complete. `tools/progress.py --check` continues to enforce evidence-on-tick and tracker consistency; it no longer emits `GATE_SKIPPED`.
- **Consequences:** the tracker can reflect actual verification progress while hardware work is pending; a later task tick does not imply that earlier device gates passed or that a phase is complete.

### ADR-085 — Verification commands and CI evidence follow the current checkout
- **Context:** the session-19 handoff, progress tracker, and Gate 11-e describe `.github/workflows/ci.yml` as the canonical Python/JVM verification workflow. Repository inspection on 2026-10-26 found that file is not tracked; the only workflow present is `.github/workflows/android-debug-apk.yml`. Treating the absent workflow as available would make the documented CI run and run URL impossible to verify.
- **Decision:** current tracked files are authoritative. Run local checks through the repository scripts and HANDOFF §5; do not claim a CI run or mark CI-dependent items complete until a verification workflow exists and actually runs. Update the stale handoff, gate, tracker, and verification-agent references to state the current absence.
- **Consequences:** X-01 and G11-e remain open, and P11-09 is blocked on restoring the previously documented workflow; local Python/JVM results remain independently recordable.
