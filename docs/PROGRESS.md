1. **Verification order:** follow the verification queue in `HANDOFF.md` §5. Tick each independently passed task as soon as its evidence is recorded, even if earlier-phase device gates remain open (ADR-084). A gate itself remains unticked until its specified procedure and evidence are complete.
2. A task is ticked only when code, tests, docs and evidence are done (see `AGENTS.md` §5).
3. Sizes: `[S]` = 1 point, `[M]` = 2, `[L]` = 4. Gates count 2 points each. Progress % is weighted by these points.
4. **Evidence:** every `[M]`/`[L]` task and every gate item has an `  - evidence:` line — fill it (commit hash, test name, log/screenshot path, device + API level). A ticked item with an empty evidence line fails `--check`.
5. In-progress: add `(WIP)` after the ID. Blocked: add `(BLOCKED: reason)` and list it under **Blockers**. **Verification ladder** (ADR-087) — at most ONE state tag right after the ID: `(WRITTEN)` code exists, unverified → `(COMPILED)` → `(UNIT-TESTED)` → `(INTEGRATION-TESTED)` → ticked `[x]` = verified. `COMPILED` and above need an `evidence:` clause. `(FAILING: reason)` records a failing check and can never be ticked. **Real-device-verified** is derived: a ticked item whose title contains `(real device)` and whose evidence has `device: <model>, Android <n> / API <n>` (an emulator never counts). Tick only after the required code, tests, docs, and verification evidence exist.
6. IDs are stable; never renumber. Add new tasks at the end of a phase with the next number.
7. After ticking: `python tools/progress.py` then `python tools/progress.py --check`; optionally `--html docs/progress.html` for a visual dashboard.
